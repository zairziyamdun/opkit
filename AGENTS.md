Данный документ обязателен для выполнения всеми AI-агентами (Cursor Agent, Claude, GPT и др.).

1. Корректность

Проект представляет собой Mini CRM систему.

Основные возможности:

- регистрация пользователей
- авторизация
- JWT
- управление задачами
- работа в реальном времени через WebSocket
- PostgreSQL

Код должен быть максимально приближен к production.

Не писать код "для тестового". Писать код как для реального коммерческого проекта.

# Архитектура Backend

Использовать модульную архитектуру NestJS.

Каждый модуль содержит:

```
module
├── controller
├── service
├── repository
├── dto
├── entities
├── interfaces
├── mapper
└── types
```

Правила:

- Controller только принимает запрос
- Service содержит всю бизнес-логику
- Repository работает только с Prisma
- Controller никогда не работает с Prisma
- Controller никогда не содержит бизнес-логику

Все зависимости внедряются через Dependency Injection.

---

# Архитектура Frontend

Использовать полноценную Feature-Sliced Design.

Структура:

```
src

app/

pages/

widgets/

features/

entities/

shared/
```

## app

Инициализация приложения.

Разрешено хранить:

- Router
- Providers
- Store
- Theme
- QueryClient
- Layout
- App

---

## pages

Сборка страницы.

Страница собирается только из widgets.

Не должна содержать сложную бизнес-логику.

---

## widgets

Крупные независимые блоки страницы.

Widget может использовать:

- features
- entities
- shared

Widget не должен знать о других widgets.

---

## features

Конкретные пользовательские действия.

Например:

- Login
- Register
- Logout
- CreateTask
- UpdateTask
- DeleteTask

Feature может использовать:

- entities
- shared

Feature не может использовать другую Feature.

---

## entities

Бизнес-сущности.

Например:

User

Task

Внутри:

```
model

api

ui

types

lib
```

Entity не должна знать о Feature.

---

## shared

Переиспользуемый код.

Например:

```
api
config
constants
hooks
lib
types
ui
utils
assets
```

Shared не знает о других слоях.

---

# Импорты

Разрешены только сверху вниз.

app
↓

pages
↓

widgets
↓

features
↓

entities
↓

shared

Запрещены обратные зависимости.

Например:

Feature не должна импортировать Widget.

Entity не должна импортировать Feature.

Shared не должен импортировать ничего выше себя.

---

# API

Все HTTP запросы находятся только внутри

```
shared/api
```

или

```
entities/*/api
```

Компоненты никогда не вызывают axios напрямую.

Запрещено:

```
axios.get(...)
```

в React-компонентах.

---

# Работа с сервером

Использовать только TanStack Query.

Запрещено вручную хранить серверные данные в useState.

---

# Формы

Использовать

- React Hook Form

совместно с

- Zod

Ручная валидация запрещена.

---

# DTO

Каждый endpoint обязан иметь DTO.

Использовать:

- class-validator
- class-transformer

Все входящие данные валидируются.

---

# Prisma

Использовать Prisma ORM.

Запрещено писать Raw SQL без необходимости.

Все изменения схемы только через миграции.

---

# WebSocket

Использовать Socket.IO.

События отправляются только после успешной записи в базу данных.

Не отправлять события до завершения транзакции.

---

# JWT

Использовать JWT Access Token.

Пароли хранить только в bcrypt hash.

Запрещено хранить пароль в открытом виде.

---

# Код

Использовать TypeScript strict.

Запрещено использовать:

- any
- ts-ignore
- eslint-disable
- unknown as any

Предпочитать:

- interface
- enum
- readonly
- Record
- utility types

---

# SOLID

Следовать принципам SOLID.

Каждый класс отвечает только за одну задачу.

Не создавать God Object.

---

# Размер файлов

Компонент:

до 200 строк.

Service:

до 300 строк.

Если файл становится слишком большим — разбить его.

---

# UI

Каждый экран обязан иметь:

- Loading
- Error
- Empty
- Success

Все кнопки должны иметь loading состояние.

---

# Git

Не изменять код, который не относится к текущей задаче.

# Перед написанием кода

AI обязан:

1. Изучить существующую архитектуру.
2. Найти похожую реализацию.
3. Использовать существующий стиль проекта.
4. Не создавать дублирование.
5. Не нарушать структуру FSD.

# Поведение AI

Перед выполнением любой задачи AI должен:

- сначала подумать о решении;
- оценить влияние изменений на архитектуру;
- изменять минимально необходимое количество файлов;
- сохранять единый стиль проекта.

При возникновении неоднозначности AI должен выбрать решение, которое лучше соответствует существующей архитектуре проекта, а не придумывать новую.

Главная цель — код уровня коммерческого production-проекта, который выглядит так, будто его писал опытный Middle+/Senior разработчик.
